## 2. 没有可靠的自动long/corner识别信号

逐一比较上述两网表，U3的全部41个封装引脚网络完全相同。角落仅比长边多`J301/F301/D301/D302/C301/C302`及`TP1～TP5`；两板共同IC型号一致。

- 没有已发现的板型ID电阻strap、EEPROM或角落独有的可探测数字器件。
- GPIO13对应U3.21，两板均为空网/NC；其他空脚的浮空电平也不能充当角色识别依据。
- 两板都有INA226，A0/A1均接GND，地址同为0x40。扫描到INA226或读取芯片标识不能区分角色。
- J301是无MCU检测连接的直流入口，PWRMUX_STATUS未连接MCU；电源电压、电流或插入适配器也不能可靠判断板形。
- 旧STUSB4500已删除，不得以0x28是否应答区分角落。MAC可作为人工登记身份的键，不能由MAC/OUI推断PCB形状。

因此默认角色应为`unknown`，不能把缺器件响应、NC脚电平或异常测量自动解释成`long`或`corner`。固件角色必须由显式构建配置或经确认的provision记录确定。

## 4. ORDER可以闭合发现，A/B是另一种电气结构

### ORDER每段是独立直邻链路

两份网表均为：

```text
前一板JOUT1.4 → 本板JIN1.4 ORDER_IN → R16 1kΩ → ESP_ORDER_IN/GPIO9
                                                      ├─ R17 10kΩ → 3V3_SYS
                                                      └─ C24 100nF → GND

本板GPIO10 → R18 1kΩ → Q1 Gate（R19 100kΩ下拉）
                      Q1 Source → GND
                      Q1 Drain  → ORDER_OUT/JOUT1.4 → 下一板输入
```

本板ORDER_IN与ORDER_OUT不是同一贯通网。审计时`include/order_link.h`的Transmitter每6秒编码**本机**boot、sequence和CRC；Link::tick分别更新接收器和发送器，不把收到的上游帧转发成下游帧。`src/order_link_io.cpp`每次启动生成随机非零boot，GPIO10控制Q1，1ms定时采样；15秒失效和采样延迟处理属于现有协议边界。

因此首尾闭合后仍是32段独立直邻链路，不会成为32个发送器共享同一根ORDER导线，也不是波形绕环无限转发。各节点可独立收发，不必先选出全环主节点才开始发信标。**可用既有直邻信标作为新环协议底层**，但仍需32板电气、调度抖动、掉线/重启和供电噪声实测。

旧服务器“无链首即conflict/cycle”是既有软件限制；总指挥已开展闭合ORDER环开发。新实现须明确完整有向环、唯一地图锚点、方向、角色数量/间距、过期边和重启映射，并验证冲突处理。本文不证明新代码已完成、已部署或环发现已实机通过。

boot是临时运行身份，不能用它做永久role记录。稳定deviceId/MAC和本次boot须建立有效映射，重启时撤销旧boot证据。4角/28长边、相邻角落间7长边是目标装配约束，可用于检查已provision角色，不能当作自动读取硬件role的证据。

### A/B每板直通，闭合后是共享电气环

BUS_A、BUS_B从JIN到JOUT直通；全部首尾对插会形成实际A/B环，两板R15在审查网表中均为DNP。ORDER的新环协议不能解决RS485反射、终端和支线问题。当前Wi-Fi/HTTP业务与ORDER可独立开发，RS485保持禁用；日后启用仍需单独冻结物理拓扑并验证。

旧文档建议断开ORDER/A/B是旧链协议下的方案。针对主任务本次“不改已下单PCB、开发闭合ORDER”的新目标，**不把ORDER断点当必需硬件改动**；A/B的限制仍保留，也不建议为本轮任务修改PCB或人为折断针脚。

## 5. 角落相对转向固定，绝对朝向未知

[接口几何审查](interconnect-audit-2026-09-21.md)记录：同一器件面朝上时，角落左侧IN公针、上侧OUT母座，方向关系固定；四角依次旋转90°可构成名义矩形周边。不能由此推断哪颗角落是绝对北向、START或屏幕显示旋转。

PCB没有方向传感器。地图锚点/起点、corner角色、屏幕旋转应分别表达；改变地图锚点不应偷偷改写硬件role。机械对插行程、跨厂家高度、接缝、长边JOUT3沿插入轴0.127mm偏差等沿用原审查限制，不在此次重复制造检查，也不以几何模型宣称实物已验收。

## 6. 推荐的角色烧录与持久化方法

首批可选择显式long/corner构建profile，或统一镜像加设备provision记录。两种方式都保留unknown默认，不自动猜测。

1. 形成32个稳定MAC/deviceId绑定的清单，经实际板形/标签确认28 long、4 corner，记录固件哈希和操作结果。COM口仅用于当次连接，不是永久身份。
2. provision至少包含schema版本、role、hardwareRevision、设备身份、batch和完整性校验；订单revision未证明时明确unknown，不从PCB2_5之类编辑器名称伪造制造revision。displayRotation可另配置。
3. 写入后commit、读回校验、重启验证，再计为烧录完成。构建role与持久化role矛盾时报告冲突并暂停自动拓扑分配，不能静默覆盖。
4. 建议在最终分区表中设置独立factory NVS，与Wi-Fi/房间/运行状态隔离；正常业务只读打开，维护流程才允许写入。损坏或版本不支持返回unknown，不在通用NVS恢复逻辑中顺带擦掉工厂区。
5. 若本批先保留原分区，可用独立namespace及应用层保护，但它不能抵御整个NVS擦除。OTA/日常升级须保留role；全片擦除会丢失记录，批量工具须根据MAC清单重新provision。
6. 不复制带设备身份、网络凭据或角色数据的同一整片Flash镜像到全部板；不烧eFuse来确定可更正的long/corner角色。

Espressif [NVS接口文档（v4.4，ESP32-S3）](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32s3/api-reference/storage/nvs_flash.html)提供独立NVS分区和只读handle接口。具体分区表、API和只读flag须核对实际Arduino/ESP-IDF版本，不能直接照搬新SDK特性；本审计未实施分区或provision工具。
